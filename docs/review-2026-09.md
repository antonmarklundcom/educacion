# Review — September 2026: what to improve, and the decisions

**Written 2026-09-11 in a planning session. Every decision below is final unless Anton
reopens it. Build sessions execute `docs/pr-plan.md` Phase 9 and `prompts/`; they do not
re-derive this document.**

## 1. The one-paragraph verdict

The code is finished. 58 PRs in four weeks produced a feature-complete, hardened, well-tested
directory (74k lines of TypeScript, ~134 test files, every SEO rule enforced by a test). The
last twenty PRs were quality work with diminishing returns, and most of them — including ones
labelled Sonnet — were built by Opus. Meanwhile the thing the plan itself calls the business
(`plan.md` §6: "a data-operations business with a website attached") has not started: the
catalog cannot fill from CONES because of a gate the pipeline enforces on itself, the ANEAES
listing has not been transcribed, no arancel exists, no career hub has editorial copy, so
**every money page is `noindex`**, and there is no evidence in the repo that the site has been
deployed. The academic search peak starts in three weeks. The improvement is not more
hardening. It is to stop building, remove the three data blockers, launch, and put the
remaining agent budget into content and the data assistant's tooling.

## 3. Findings, ranked by what they cost

### F-1 — The modality gate blocks the whole catalog (critical)

`pipeline.ts` refuses to create an offering when CONES prints no modality, citing rule 1. The
reasoning was right (defaulting to `presencial` is fabrication) and the outcome is wrong: the
register no longer prints modality for *anyone*, so the honest gap became "no catalog". Rule 1
asks for the honest gap to be *shown*, not for the row to be withheld. `enrollment_status`
already has a `sin_datos` value for exactly this reason.

**Decision:** add `sin_datos` to `MODALITY`; CONES rows become offerings with
`modality = 'sin_datos'`; the UI prints "Modalidad: sin datos"; the modality filter never
matches them; JSON-LD omits `courseMode` for them. This is PR-59 and it is the most valuable
change left in the repository. Opus, because it is a schema and search-contract change.

### F-2 — The ANEAES transcription was recommended and never scheduled (critical)

`data-sources.md` §1.2 already contains the correct analysis (transcribe, don't parse). It
sat as "open" for a month because no PR owned it. **Decision:** transcribe. Anton commits the
12-page PDF; a Sonnet session transcribes it into the CSV contract §1.2 defines and proves the
row counts against the PDF's own totals; an Opus session reviews before merge because this is
the field with legal exposure. PR-62.

### F-3 — Aranceles have no collection path that scales (high)

The playbook (`data-sources.md` §5) says 600–900 offerings collected by a data assistant.
The admin offers one form per price. That assistant will work in a spreadsheet; the site needs
to ingest the spreadsheet through the same validation the form uses, with a dry-run and
per-row errors. **Decision:** PR-61, Opus, because the CSV header contract is the assistant's
template and expensive to change afterwards. The assistant is a human-inputs item (§7), hired
now, not after launch.

### F-4 — The money pages are `noindex` until someone writes 150 words each (high)

Correct rule, nobody owns the writing. **Decision:** editorial copy for the top careers is
agent-written from checked-in markdown, seeded only where `description_md` is null, reviewed
against the fabrication checklist before merge. No number in the markdown, ever — counts,
prices and durations are rendered by the page from the database. PR-63. Three accreditation
posts for the hub follow the same path from sources Anton supplies. PR-64.

### F-5 — Nothing stops the preview host being indexed (medium, cheap)

There is no middleware. Once deployed, `*.hostingersite.com` and any secondary domain serve a
full duplicate of the site. `NEXT_PUBLIC_SITE_URL` fixes canonicals, not crawling.
**Decision:** a host-canonical middleware that 301s every non-canonical host to the canonical
one, path preserved, and `robots` that disallows everything on a non-canonical host. PR-60.
This is also the whole implementation of the domain decision in §5.

### F-6 — The model split drifted (process)

Phase 8's four PRs and the PR-40–42 "built by Opus 5" notes show Opus doing Sonnet-labelled
work. Each one costs about twice. **Decision:** the phase table's model column is binding.
Every Phase 9 PR has a prompt file in `prompts/`; a session runs one prompt and ends. Fable
appears only in the planning conversation that wrote this document and, optionally, once after
the Opus lane merges (`prompts/README.md`).

### F-7 — Docs are the largest per-session cost (process)

`architecture.md` is a 3,100-line changelog. Every session is told to read the area doc;
the area doc is now most of the history. **Decision:** PR-66 splits the "settled in PR-NN"
sections into `docs/decisions/`, leaves `architecture.md` as current state, and updates the
`CLAUDE.md` table. Sonnet, last in the lane, after the launch PRs.

### F-8 — Hardening is done (process)

No further coverage, audit, sweep or Lighthouse PR is scheduled. A new one needs a defect it
fixes, named in its title. `risks.md` §R-15 applies to hardening as much as to features.

## 5. The multi-domain question

Anton owns `educacion.com.py` and `universidad.com.py`, and is considering `colegio.com.py`
and `escuelas.com.py`, served from one Node.js app. Google Keyword Planner (Paraguay, monthly):

| Keyword | Volume | 3-mo | YoY | Competition |
| --- | --- | --- | --- | --- |
| escuelas | 9,900 | −18 % | −18 % | low |
| profesor | 9,900 | +179 % | −45 % | low |
| estudiante | 9,900 | +179 % | −70 % | low |
| universidad | 4,400 | +86 % | +23 % | low |
| educacion | 3,600 | 0 % | −19 % | low |
| colegio | 3,600 | +24 % | +24 % | low |
| becas | 1,000 | −18 % | −18 % | low |
| estudios | 1,000 | 0 % | −12 % | low |

Reading it honestly: these are single-word head terms with no intent, and the whole table is
under 45k searches a month. The traffic model (`seo.md` §1) is the long tail — thousands of
`[carrera] + [ciudad]` queries — and a domain's exact-match word contributes almost nothing to
that. What a second domain *does* do is split authority, duplicate content and double the
sitemaps, Search Console properties, OG origins and cookie domains.

**Decisions** (full reasoning in `docs/domains.md`):

1. **One canonical domain: `educacion.com.py`.** It is the umbrella that a later colegios
   section fits under; `universidad.com.py` is not.
2. **`universidad.com.py` becomes a 301 to `educacion.com.py/universidades`** at the hosting
   or DNS level, with the app's host middleware (PR-60) as the backstop. Not a second site,
   not a mirror. No rebrand.
3. **`colegio.com.py` / `escuelas.com.py`: do not buy them for a product.** Buy at most one
   as a defensive redirect if the price is trivial. A K-12 directory is a real second product
   with a bigger sellable universe than universities (private colegios outnumber private
   universities by an order of magnitude) — and it ships, if ever, as `/colegios` on
   `educacion.com.py`, Phase 10, after the first paying institution. Its data source is
   MEC's open institution register, not CONES/ANEAES, and it reuses the institution →
   offering → price → comparador shape unchanged.
4. **Multi-host routing in one Next.js app is kept as a documented option, not built.**
   `docs/domains.md` §4 holds the design (host → section rewrite in middleware, per-host
   canonical, cookie domain per host) so nobody re-derives it. Trigger: a section that has its
   own audience and needs its own brand, plus confirmation that a Hostinger managed Node.js
   app can carry more than one domain (human-inputs item — unverified from here).
